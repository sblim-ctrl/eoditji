## 01. Executive Summary

**문제**: 가끔 쓰는 물건의 위치를 넣은 사람조차 기억하지 못해, 필요한 순간마다 집 안을 뒤지며 시간을 쓴다.

**해법**: 수납칸 하나를 사진 한 장으로 기록해 두면, 나중에 다른 이름으로 말해도 그 칸과 사진을 보여 준다.

**대상**: 자취하는 2030(넣는 사람 = 찾는 사람)으로 확정했다. 설문에서 자취 7명은 모두 계절 정리를 '내가 직접' 했고, 가족과 사는 13명 중에서는 1명뿐이었다(02 근거). 가족과 사는 사람은 정리를 '함께' 하는 경우가 많아(8명) 그룹 공유(P1)와 함께 다음 타겟으로 본다.

**이번 범위**: 1차 MVP. 11/3(화) 09:50 제출이다. 로그인과 내 기록 저장까지 실서비스로 배포하고, 그룹 공유는 시간이 남을 때 붙인다.

**성공의 한 문장**: 찾기 질문 30건에서 정답 서랍을 85% 이상(다른 이름으로 물은 질문은 80% 이상) 맞히고, 기록에 없는 물건은 지어내지 않으며, 칸 하나를 기록하는 AI 비용은 1센트 이하다.

**용어**: 칸은 사진 한 장으로 기록하는 서랍·수납장 한 칸이다. 공간은 칸이 속한 방이나 가구(책상, 안방 옷장)다. 그룹은 기록을 함께 쓰는 단위("우리 집")다.

**일정이 밀리면 자르는 순서**: P1 그룹 → P1 앱 안 카메라 → 저장 후 칸 상세에서 고치기(공간 바꾸기 포함) → EODI 대화 상대. 라벨 저장과 평가 스크립트는 수치 근거라서 자르지 않는다.

### 지금은 안 하는 것과 이유

| 하지 않는 것 | 이유 | 다시 볼 조건 |
|---|---|---|
| 그룹 공유를 P0로 넣기 | 1차의 핵심 가설은 '기록하게 만들기'와 '다른 이름 검색'이다. 공유는 그다음 문제다 | P0가 11/1에 끝나면 P1로 진행 |
| 물건 단위로 숨기기 | 공유한 칸의 사진에 찍힌 물건은 목록에서 숨겨도 사진으로 보인다. 숨기려면 칸 전체를 끄는 쪽이 안전하고 단순하다 | 사진 부분 가리기 기능이 생긴 뒤 |
| AI가 기록을 자동으로 고치거나 지우기 (Decide) | 신뢰를 쌓기 전에는 AI가 결정하지 않는다. 위치 후보와 근거를 보여 주는 데까지만 한다 | 수정 없이 쓴 비율이 충분히 높아진 뒤 |
| 질문마다 기록 전체를 LLM에 넣기 | 기록이 늘수록 비용과 지연이 커지고, 지어낼 여지가 생긴다 (05의 검색 비용 전략) | 없음 (평가 기준선 v1로만 사용) |
| 쟁여둔 소모품 재고 관리 | 쓰면 줄어들어 기록이 빨리 낡는다. 5일 범위 밖이다 | 설문 Q9에서 조건 충족(못 찾아서 다시 산 적 45%, 자취 6/7, 대부분 소모품). 1차 MVP 이후 확장 후보로 다시 본다 |
| 매일 쓰는 물건 (열쇠, 지갑) | 위치가 매번 바뀐다. 위치 추적 태그가 이미 해결 중이다 | 없음 |
| 화장대·욕실 기록 | 처방약 같은 건강정보가 사진에 찍힐 수 있다 | 민감정보 가리기가 생긴 뒤 |
| 계절 선제 알림, 보관 라벨 문구, 출력용 보관 지도 | 핵심 흐름 밖이다 | 확장 로드맵 |

## 02. Discovery 요약

### Sharp Problem

| 요소 | 내용 |
|---|---|
| Who | 계절 정리를 직접 하는 자취 2030 (B, 설문으로 확정) |
| When | 환절기에 몇 달 전 넣어 둔 물건이 처음 필요해지는 날, 또는 갑자기 물건이 필요해진 순간 |
| Cost | 계절 옷·이불 찾기에 1시간 × 2명. 넣은 사람도 위치를 확신하지 못함 |
| Evidence | 가족에게 물어보기, 기억에 기대어 뒤지기 같은 우회 행동 |

### 근거

- 본인 경험: 계절 옷·이불을 엄마와 1시간 동안 찾았고, 엄마도 위치를 확신하지 못했다. 이어캡은 책상 서랍 안에 있었는데 찾는 데 시간이 걸렸다.
- 설문: 10/29~10/30 구글 폼, 20명 응답(가족과 함께 13, 자취 7). 배포한 폼에서는 Q12가 'Q11-2'로 번호가 바뀌었다.

| 문항 | 판단 기준 (사전 고정) | 결과 |
|---|---|---|
| Q3 경험 비율 | '있다' 30% 미만이면 주제 재검토 | 17/20(85%) '있다' → 주제 유지 |
| Q1 × Q2 | 사는 형태별 '내가 직접' 비율이 높은 집단을 타겟으로 | 자취 7/7(100%), 가족과 함께 1/13(8%) → **B 자취 2030 확정**. 가족과 함께는 '함께' 8/13 |
| Q5 걸린 시간 | 15분 이상 비율을 문제 크기 근거로 | 15분 이상 9/17(53%), '결국 못 찾음' 3명 포함 시 12/17(71%). 1시간 이상 4명 |
| Q7 발견 위치 | 서랍·상자 안이 절반 이상이면 "열고 찍기", "사진 + 한 줄 메모"를 필수 설계로 | 서랍·상자 안 5/17(29%) → 기준 미달, 필수 설계 추가 없음. 옷장·수납장 안(5)까지 닫힌 수납으로 보면 10/17(59%)이라 '칸을 열고 찍는' 핵심 흐름과는 맞음 |
| Q11·Q12 기록 경험 | '해 봤지만 그만뒀다'가 많으면 기록 부담이 병목이라는 가설을 뒷받침 | 그만뒀다 2/20(10%) → 기준 미달. 대신 '해 본 적 없다' 18/20(90%), 지금 기록하는 사람 0명. 기록하다 지친 게 아니라 기록 습관 자체가 없음 → 가장 위험한 가정 1이 더 중요해짐 |
| Q12 그만둔 이유 | 가장 많은 이유를 회의록의 기록 부담 대응표로 설계에 반영 | 17명 응답. '넣을 땐 기억할 줄 알아서' 8(47%), '기록하기 번거로워서' 6(35%), '기록할 생각을 해 본 적 없음'(기타) 1, 기타 2. 1위는 대응표의 '기록할 계기가 없음' → 대응책으로 '찾은 직후 찍기'를 P0에 추가 |

- 그 밖의 결과: 찾는 방법은 17명 모두 '기억나는 곳부터 직접 뒤짐'이었다. 못 찾아서 새로 산 적이 있는 사람은 9/20(45%)이고 자취는 6/7이었다. 산 물건은 건전지, 립밤, 화장품, 상비약처럼 대부분 소모품이다.
- 한계: 응답자가 캠프 동료라 2030·IT 친숙 쪽으로 치우친다. 자취 응답이 7명뿐이라 비율은 방향만 본다.

### Proto-persona

설문 응답(자취 7명)으로 만든 가설이다. 사용자 테스트(3~5명)에서 확인한다.

| 항목 | 내용 |
|---|---|
| 누구 | 원룸·오피스텔에 혼자 사는 20대 후반~30대 직장인. 계절 정리와 수납을 혼자 한다 |
| 최근에 찾은 물건 | 겨울 옷, 보온물주머니, 치실, 줄자, 모니터 지지대. 계절 물건과 가끔 쓰는 생활용품 |
| 있던 곳 | 서랍 안 3, 옷장·수납장 안 3, 끝내 못 찾음 1 |
| 지금 찾는 법 | 기억나는 곳부터 직접 뒤진다. 물어볼 가족이 없다. 위치를 기록하는 사람은 없다 |
| 기록하지 않는 이유 | 넣을 땐 기억할 줄 알았다(3), 넣을 때마다 기록하기 번거롭다(3) |
| 치르는 비용 | 15분 이상 걸리거나 못 찾음 4/7. 못 찾아서 다시 산 적 있음 6/7 |
| 그때의 말 | "500개짜리 샀는데.. 아 그냥 또 살까.. 분명 여기 넣어놨는데..." / "어디 있는지 모르겠고 자괴감이 조금 들고 짜증도 납니다" |
| 필요한 것 | 넣을 때마다가 아니라 정리하는 날 한 번에 기록하기, 다른 이름으로 물어도 그 칸과 사진을 보여 주기 |
| 대상 아님 | 가족과 살며 정리를 남이 하거나 함께 하는 사람(A). 그룹 공유(P1)가 생긴 뒤 다음 타겟 |

### 가장 위험한 가정

| 순위 | 가정 | 검증 | 지표 | 상태 |
|---|---|---|---|---|
| 1 | 정리하는 날 사진으로 기록해 줄 것이다 | 사용자 테스트 3~5명 | 기록 완료율, 1칸 기록 시간 | 검증 못 함: 11/2 사용자 테스트 취소(시간). 합성 이미지 실험은 인식 조건만 봄 |
| 2 | AI가 서랍 사진에서 작은 물건까지 인식할 것이다 | 서랍 사진 10장 | 인식률, 박스 적중률 | 11/1 예정 |
| 3 | 다른 이름으로 물어도 찾아 줄 것이다 | 찾기 질문 30건 | 정답 서랍 일치율 | 11/1 예정 |
| 4 | 문제가 풀 만큼 크다 | 설문 Q3·Q5·Q9 | 경험 비율, 걸린 시간, 중복 구매 | 10/31 확인: 경험 85%, 15분 이상 53%(못 찾음 포함 71%), 중복 구매 45% |

### 우선순위 (PAUF → 2x2)

Use Case는 "순간 × AI 역할 × 결과"로 적었다. 점수는 항목당 1~3점이며 1점 차이는 중요하지 않다.

| Use Case | P | A | U | F | 판단 |
|---|---|---|---|---|---|
| 정리하는 날, AI가 서랍 사진으로 목록 초안을 만들어 기록 부담을 줄인다 | 3 | 2 | 3 | 2 | High Impact |
| 갑자기 필요할 때, 다른 이름으로 물어도 AI가 칸과 사진을 찾아 준다 | 3 | 3 | 3 | 3 | High Impact |
| 저장 직후, AI가 다른 이름의 추천 질문으로 바로 검색해 보게 한다 | 2 | 2 | 2 | 3 | Quick Win (핵심 흐름 안) |
| 초안에서 AI가 본 위치를 보여 주고, 사용자가 고친 것을 라벨로 모은다 | 2 | 2 | 2 | 2 | Quick Win (신뢰와 학습 데이터) |
| 가족이 넣은 물건을 그룹 기록에서 찾는다 | 2 | 1 | 3 | 2 | AI 기능은 아님. P1 |
| 날씨를 보고 계절 물건 위치를 먼저 알려 준다 | 1 | 1 | 2 | 2 | Too Early |
| 쟁여둔 소모품 재고로 중복 구매를 막는다 | 1 | 2 | 1 | 1 | Do Not Build (지금) |

### 개선 전후 비교

같은 30건으로 네 버전을 잰다. 각각 유형별 정답률, 지어낸 답 수, 1회 비용, p95 지연을 본다. 같은 질문을 5번 반복해 답이 같은지도 본다.

| 버전 | 방식 |
|---|---|
| v0 | 키워드 검색 (프로토타입의 `keywordSearch`). 비용 0원 |
| v1 | 그룹 기록 전체를 LLM에 넣는 방식 (프로토타입 방식) |
| v2 | 단계별 검색 (05의 검색 비용 전략) |
| v3 | v2의 실패를 유형별로 분석해 고친 버전 |

발표 문장 목표: "정확도는 X%에서 Y%로 오르고, 검색 1회 비용은 Z% 줄었다."

## 04. 요구사항 번역

### 비즈니스

- 목표: 1차에서는 "사진 한 장 기록 → 다른 이름 검색"이 실제 서랍으로 돌아간다는 것을 수치로 보인다.
- 제약: 마감 11/3 09:50, 개인 프로젝트, 실제 집 사진이라는 민감 데이터.
- 가드레일: 사용자별 일일 호출 한도(인식 20회, 검색 100회), OpenAI 월 예산 한도, 다른 사람 데이터 노출 0건.

### 사용자

**사용자 스토리**

- 기록: 사용자로서 나는 정리하는 날 서랍 앞에서, 나중에 다시 찾을 수 있게, 사진 한 장 찍고 빠진 물건만 한 줄 보태고 싶다.
- 검색: 사용자로서 나는 물건이 갑자기 필요해진 순간에, 집을 뒤지지 않으려고, 떠오르는 이름 그대로 말해서 어느 칸인지 보고 싶다.
- 공유(P1): 사용자로서 나는 가족이 넣어 둔 물건이 필요할 때, 가족에게 묻지 않으려고, 우리 집 기록에서 찾고 싶다. 단, 내 칸 중 보여 주기 싫은 칸은 끌 수 있어야 한다.

**성공 경험**

| 요소 | 내용 |
|---|---|
| Outcome | 서랍 앞에 가서 바로 꺼낸다 |
| Moment of Truth | "이어팁 어디 있어?"에 "책상 왼쪽 첫째 서랍, 검정 파우치 안"이 사진과 함께 나올 때 |
| Acceptance | 답을 보고 다시 묻지 않고 그 칸을 연다 |
| Trust Cues | 그 칸 사진, 사진 위 박스, 찍은 날짜, 누가 찍었는지(P1) |

**실패할 때의 최소 보상**: 못 찾으면 '기록 없음'이라고 솔직하게 말하고, 칸별 물건 목록을 보여 준다. 틀렸다면 "거기 없던데?" 한 번으로 다시 찍기로 이어 준다.

| 검색 2단계, 다른 이름 생성 | `gpt-6-luna` | $0.10 / $0.50 | 현역 모델 중 가장 쌈 |
| 임베딩 (P1) | `text-embedding-3-small` | $0.02 (입력만) | |
| 음성 받아쓰기 (P2) | `gpt-transcribe` | 분당 $0.0045 | |

**호출 설정**
- Responses API, 구조화 출력(strict), `store: false`. 대화 상태를 OpenAI에 저장하지 않는다.
- 추론 강도는 검색 `none`, 인식 `low`로 시작한다.
  - 기본값 `medium`은 추론 토큰이 출력 요금으로 청구된다.
  - 정확도와 함께 평가에서 비교한다.
- 이미지는 1400px JPEG를 `detail: "original"`로 보낸다(공식 문서가 좌표가 중요한 작업에 권장).
  - 1400×1050이면 약 1,743토큰이다(44×33 패치 × 1.2).
  - D1 실측: 사진 1장 + 프롬프트의 입력이 두 모델 모두 약 2,350토큰이다. luna·terra의 이미지 배수는 1배로 본다.
- 평가 스크립트는 Flex 처리(표준가의 50%)로 돌린다.

**예상 비용** (1달러 ≈ 1,400원 가정)

| 호출 | 1회 |
|---|---|
| 사진 인식, terra | **실측 평균 $0.0067 (약 9원)**. 출력 555~1,317토큰이라 칸에 물건이 많을수록 비쌈 (추정은 $0.0094) |

- 1차 전체(인식 약 150회, 검색 약 800회)는 약 $2이다. OpenAI 월 예산 한도는 $20로 건다.
- **비용의 대부분은 사진 인식이다.** 그래서 비용을 줄이는 우선순위는 인식 모델 선택(terra와 luna 비교)과 사진 크기다.
- **인식 1회는 10~20초 걸린다** (D1 실측, 두 모델 비슷. luna는 추론 토큰을 4~5배 더 써서 빠르지 않음). 그래서 기다리는 동안 공간을 묻는 설계가 필요하다.

**GPT-5 계열을 쓰지 않는 이유**
- 같은 급에서 GPT-6보다 비싸다 (5.1, 5.4, 5.6).
- 더 싼 `gpt-5-nano`·`gpt-5-mini`는 지원 종료 예정(2026-12-11 서비스 중단)이라 2차 전에 다시 옮겨야 한다.
- 둘 다 파인튜닝도 지원하지 않는다.

### Input

| 층위 | 사진 인식 | 검색 |
|---|---|---|
| User Input | 서랍 사진(1400px JPEG, EXIF 제거), 칸 이름 | 질문 문장 (글 또는 음성 받아쓰기) |
| Context Input | 대화 상대(엄마/EODI) | 후보 물건 최대 20개 (id, 이름, 다른 이름, 공간과 칸, 담긴 용기), 대화 상대 |
| Instruction | 확실/추정/가려짐 기준, 박스 좌표 형식, 다른 이름 생성 규칙, 질문 말투 | 후보 밖의 답 금지, 판단 불가면 confidence low |

### Output 스키마

사진 인식 (구조화 출력, strict):

```json
{
  "sure":   [{ "name": "가위", "box": [120, 80, 260, 210], "aliases": ["가윗", "자르는 거"] }],
  "guess":  [{ "name": "줄자", "box": [600, 400, 700, 520], "aliases": ["메저"] }],
  "hidden": [{ "name": "검정 파우치", "box": [100, 500, 380, 800], "aliases": ["검은 주머니"] }],
  "questions": [{ "target": "검정 파우치", "ask": "검정 파우치 안엔 뭐 들었어?" }],
  "try": ["자르는 거 어디 있어?"]
}
```

- `box`는 `[x1, y1, x2, y2]`, 0~1000 정규화 정수이며, 모르면 `null`이다.
- Uncertainty는 `guess`(일부만 보임)와 `hidden`(안이 가려짐)으로 드러낸다.

검색 (2단계 LLM):

```json
{ "intent": "find", "itemIds": ["<후보 id>"], "confidence": "mid" }
```

- `itemIds`는 JSON 스키마 enum으로 이번 후보의 id만 허용한다. 그래서 없는 물건은 형식 단계에서 나올 수 없다.
- 답 문장은 LLM이 아니라 대화 상대 템플릿이 만든다.

### 기능별 스펙

| 기능 | Output | 성능 목표 | 실패 정의 | Fallback |
|---|---|---|---|---|
| 사진 인식 | 위 스키마 | 인식률 ≥ 80% | 보이는 물건을 빠뜨림, 없는 물건을 만듦 | 빼기와 직접 추가. 인식 실패 시 직접 입력 모드 |
| 위치 박스 | 물건별 `box` 또는 `null` | 적중률 ≥ 60% | 엉뚱한 곳에 박스, 박스 없음 | '여기 아니야' → 옮기기·다시 그리기. 적중률이 낮으면 '대략 위치', 거의 틀리면 3×3 칸 고르기로 표시 |
| 다른 이름 검색 | `{intent, itemIds, confidence}` | 일치율 ≥ 85%, 지어낸 답 0 | 틀린 칸, 지어낸 물건 | 아래 Confidence별 화면 |
| 추천 질문 | 질문 3개 | 클릭률 측정 | 목록과 같은 이름을 반복 | "나중에 할게" |
| 시스템 오류 | — | — | OpenAI 오류·시간 초과, 일일 한도 초과(429) | 검색: 키워드 검색(v0)으로 대신 찾고 그렇게 찾았다고 알림<br>인식: 직접 입력 모드<br>한도 초과: 대화 상대 말투로 내일 다시 하라고 안내 |

### Confidence별 화면

| Confidence | 화면 |
|---|---|
| high | 답과 칸 카드(사진, 박스, 찍은 날짜)를 바로 보여 준다 |
| mid (다른 이름으로 찾음) | "이 물건 맞아?"와 함께 카드를 보여 준다 |
| low 또는 모호한 질문 | 후보 칸 목록을 보여 주고 고르게 한다 |
| 못 찾음 | '기록 없음'이라고 답하고 칸별 물건 목록으로 이어 준다 |

### 실패 택소노미

| 유형 | 예 | 대응 |
|---|---|---|
| 의도 오해 | "여행 갈 때 챙길 거"를 물건 하나로 해석 | low → 후보 목록 |
| 지식 오류 (지어냄) | 기록에 없는 손톱깎이를 있다고 답함 | 후보 enum으로 차단, 서버에서 한 번 더 확인 |
| 확신 부족 | 이어팁과 이어캡을 이을지 망설임 | mid → 확인 요청 |
| 데이터 실패 | 불투명 파우치 안 물건은 사진만으로 알 수 없음 | 기록 단계의 가려진 곳 질문으로 보완 |

### 리스크 허용 기준

| 등급 | 대상 | 대응 |
|---|---|---|
| High (차단) | 없는 물건을 지어냄 | 후보 enum + 서버 확인, 실패하면 `found=false` |
| High (차단) | 다른 그룹, 또는 남이 공유를 끈 칸이 보임 | DB 권한 규칙(RLS)으로 목록·검색·사진을 모두 막음 |
| Medium (경고 + 수정) | 다른 이름으로 찾음 | 확인 요청 |
| Low (허용 후 개선) | 추정 물건 | 표시만 함 |

### 검색 비용 전략

- 수납칸 기록은 드물고 검색은 자주 일어난다. 그래서 "이어팁 = 이어캡" 같은 연결을 **저장할 때 한 번** 만들어 둔다.
  - 인식 호출 한 번에 물건마다 다른 이름 3~6개를 함께 받는다.
- 검색은 싼 단계부터 시도한다.

| 단계 | 하는 일 | 비용 |
|---|---|---|
| 0단계 (브라우저) | 이름·다른 이름과 정확히 하나만 일치하면 바로 답 | 0원 |
| 1단계 (서버) | 비슷한 후보 20개로 좁힘 | 저렴 |
| 2단계 (작은 LLM) | 그 후보 중에서만 고름 | 입력 토큰이 크게 줄어듦 |

- **비용보다 중요한 이득**: v1 방식도 검색 1회가 1원 미만이다. 그래서 단계별 검색의 주된 이득은 세 가지다.
  - 0단계의 즉시 응답
  - 지어냄 차단
  - 기록이 늘어도 비용과 지연이 커지지 않음
- **쓰면 쓸수록 정확해진다**: LLM 단계로 찾고 "찾았어!"를 누르면, 그 질문 표현을 다른 이름으로 배운다. 다음부터는 0단계에서 공짜로 찾는다.
- **위험 대응**
  - 0단계는 정확히 하나만 일치할 때만 답한다.
  - "거기 없던데?"가 오면 그 다른 이름을 지운다.
  - 후보 안에 정답이 들어간 비율(recall)을 평가에서 따로 잰다.
- 상세는 [개발계획.md](개발계획.md#5-검색-비용-전략)에 있다.

### AI가 본 위치와 라벨 (지도학습 데이터)

- 물건을 누르면 사진 위에 AI가 본 박스를 보여 준다. 사용자는 맞아 / 위치 고치기 / 이름 고치기 / 빼기 / 추가를 할 수 있다.
- 모든 행동은 `item_labels`에 지우지 않고 쌓인다.

| 행동 | 학습 신호 |
|---|---|
| 맞아 | 정답 |
| 옮기기 | 고친 정답 박스 |
| 빼기 | 오검출 |
| 추가 | 누락 |

- 이 기록에서 Edit Rate와 박스 적중률을 계산한다.
- 학습 경로(2차): 같은 집 정답 예시를 프롬프트에 넣는 few-shot → 박스가 계속 부정확하면 COCO로 내보내 전용 탐지 모델.
  - `gpt-6-luna`·`gpt-6.1-terra`는 파인튜닝을 지원하지 않는다.
  - 그래서 OpenAI 파인튜닝은 지원 모델이 생길 때 다시 본다.
- OpenAI 공식 문서도 "The model struggles with tasks requiring precise spatial localization"이라고 적고 있다.
  - 이전 GPT 모델도 박스 좌표가 자주 틀린다는 보고가 있다.
  - 그래서 D1에 사진 3장으로 먼저 확인하고 표시 방식을 정한다.

### 개인정보와 안전

- 사진은 비공개 저장소에 두고, 짧게 만료되는 서명 URL로만 보여 준다.
- 사진을 다시 JPEG로 저장하면서 EXIF(GPS 위치 포함)를 지운다.
- 첫 촬영 전에 "사진은 물건 목록을 만드는 데만 써요"라고 알린다.
- 학습용 내보내기는 아래 조건을 모두 만족하는 행만 대상으로 한다.
  - 동의한 사용자 (`allow_training`, 기본 꺼짐)
  - 민감 물건이 없는 칸
  - 사람이 한 번 검토함
- 화장대·욕실 기록은 보류한다.
- OpenAI API 데이터 정책 ([Your data](https://developers.openai.com/api/docs/guides/your-data), 2026-10-30 확인)

| 항목 | 내용 |
|---|---|
| 학습 | API로 보낸 데이터는 기본적으로 모델 학습에 쓰이지 않는다 (직접 동의할 때만) |
| 보관 | 남용 감시 로그로 최대 30일 보관한다 |
| 대화 상태 | Responses API는 기본 30일 저장하므로 `store: false`로 끈다 |
| 보관 0일(ZDR) | 영업팀 승인이 필요해 1차에는 해당하지 않는다 |
| 이미지 검사 | 이미지는 아동 성착취물(CSAM) 검사를 거치고, 탐지되면 보관된다 |
| 처리 위치 | 한국 리전은 저장만 지원하고 처리는 하지 않으므로, 사진은 미국에서 처리된다 |

- 첫 촬영 안내 문구: "사진과 질문은 물건을 정리하고 찾기 위해 OpenAI로 보내져 미국에서 처리돼요. OpenAI는 이 데이터를 학습에 쓰지 않고, 남용 감시를 위해 최대 30일 보관할 수 있어요."
